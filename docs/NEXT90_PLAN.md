# One focus, three controllable goals

Decision prepared early on 2026-10-11 at the owner's request. The current plan ends 2027-01-09; the proposed following 90-day period is **2027-01-10 through 2027-04-09 inclusive**. No claim is made that the first period is complete.

## Focus: maintain and finish Maze Signal

Keep Maze Signal as the main public project. Its installation-free demo has the smallest path from a visitor to a reproducible result, a defined educational audience and a bounded maintenance backlog. Keep CrashVault, Faultline and PowerControlLab as portfolio evidence with regression maintenance. Do not start another showcase repository to replace missing real feedback.

This is a provisional choice based on project scope and the owner's requested direction, not proven demand. There is no independent feedback yet. Reconsider the focus if actual reports favor another project or maintenance exceeds available time.

## Goal 1 — maintain the demo and release only verified changes

Keep new features within the existing small issues. This turn prepares reduced-motion initialization and CLI map export; record their actual checks and any remaining OS/device checks. For future bugs, preserve the exact map, reproduce the failure and attach relevant verification to the fix. Keep CI green before release. Completion: bounded issues have documented outcomes, verification and a linked release; no guaranteed response-time commitment.

## Goal 2 — make real first-use feedback possible

Prepare one clear 30-second test request and ask the owner to share it with 5–10 willing, relevant people. Invitations need specific recipients or a permitted community before any agent sends them. Publish only consented, anonymized real reports. Completion of our controllable work: test request, reproducible issue templates and triage instructions are ready. Responses, repeat use and accepted PRs remain external outcomes; do not tick those without evidence.

Test request: “Open https://mohammmad357.github.io/maze-signal/ without additional help. Run one comparison, change a wall or terrain weight, then export the map. What confused you, what helped, and what is missing? Include your browser/device and the map text if anything fails.”

## Goal 3 — publish a small maintenance record

During each active maintenance week, record actual work, test results, open blockers and a small educational example when useful. At the end, compare followers/stars separately from reported users, real feedback and outside participation. Publish actual income/expenses only if a verified financial channel is activated; otherwise state no verified destination. Completion: dated records plus a final evidence-linked report. Follower counts, donation totals and star targets are not guaranteed deliverables.

## Capacity and carry-over

Proposed 6–8 hours/week: 1 triage, 3 bounded fixes/testing, 1 documentation, 1 CI/release, up to 2 buffer. This is a plan, not measured personal capacity. If only four hours are available, prioritize triage/correctness and defer new content.

Carry over: independent first-use review, real invitation/feedback, return-use evaluation, review responses when human comments arrive, feedback-led release, verified support destination and the final 90-day report. Real-device touch testing and reduced-motion OS verification must not be replaced with desktop screenshots. Report unknowns instead of filling them with hypothetical 8.5/10 scores.
